Plan it in folders. Build it in folders.

btdstudio is three small Go CLIs for spec-first, AI-assisted software work. The filesystem is the architecture, your approvals are the gates, and any AI harness can follow along. So can you, without one.

go install github.com/btdstudio/daiku/cmd/daiku@latest

Requires Go. kumi and hanga install the same way, when you need them.

How it works

From a plan to a pull request.

One daiku workspace has a room for each kind of work. The plan room and the build room connect through one thing, a markdown ticket, with no shared runtime and no service in the middle.

01

Plan behind gates

An initiative moves through intake, spec, architecture and breakdown, with research, explore and synthesis when you need them. You and your AI harness write the files, each phase waits for your approval, and the plan ends in tickets.

$ daiku init acme && cd acme
scaffolded daiku workspace in acme
$ daiku repo add webapp git@github.com:acme/webapp.git \
    --path ~/src/webapp
added webapp — commit REPOS.json to share it
$ daiku change new "Customer accounts" --repo webapp
created room plan/
created change 1-customer-accounts (source #1)
synthesis skipped
$ daiku gate breakdown approved
daiku: breakdown requires intake to be approved (currently "draft")
daiku: breakdown approved: 1 artifact problem(s):
  plan/specs/1-customer-accounts/tickets: no tickets
(pass --force to override)
$ daiku gate intake approved
1-customer-accounts: intake = approved
$ daiku gate research skipped --reason "new app"
1-customer-accounts: research = skipped
$ daiku gate explore skipped --reason "new app"
1-customer-accounts: explore = skipped
# write the functional spec and the architecture
$ daiku gate spec approved
1-customer-accounts: spec = approved
$ daiku gate architecture approved
1-customer-accounts: architecture = approved
$ daiku tickets new story "Add password reset" \
    --repo webapp --requirements R1
created S-0001 plan/specs/1-customer-accounts/tickets/S-0001.md
# write the acceptance criteria
$ daiku gate breakdown approved
1-customer-accounts: breakdown = approved
02

Hand off a ticket

Tickets are the only interface between the plan room and the build room. Once breakdown is approved, a ready ticket starts a build: one change in one repo. The ticket is plain markdown, so it can also come from your PM tool, or go to any other harness.

$ daiku tickets ready --all
S-0001: ready
$ daiku build new S-0001
created room build/
created build S-0001 for webapp (plan/specs/1-customer-accounts/tickets/S-0001.md)
03

Land it in the repo

Approvals don't carry over, because a build approves something different: how this ticket lands in this repo. It runs through requirements, design and tasks, then implement, test, review, security and ship, and ends in a pull request that links the ticket. One build per repo writes code at a time.

$ daiku gate ticket approved
S-0001: ticket = approved
$ daiku gate requirements approved
S-0001: requirements = approved
$ daiku gate design approved
S-0001: design = approved
$ daiku gate tasks approved
S-0001: tasks = approved
$ daiku gate implement in-progress
S-0001: implement = in-progress
$ daiku status

The tools

Three CLIs. Use one or all of them.

daiku

大工

carpenter

Plans initiatives that take weeks and span many repos, then builds each ticket in one repo through to a pull request, for any AI harness or none.

  • A plan room: research, spec, architecture and breakdown, each behind a gate
  • A build room: requirements to ship, including test, review and security
  • Tickets as markdown, which an agent can sync with your PM tool
  • Approvals committed to git, so they survive a clone
go install github.com/btdstudio/daiku/cmd/daiku@latest
Read the daiku docs on GitHub

kumi

組

assembly

Scaffolds Go + HTMX + Bootstrap 5 web apps with the unglamorous parts already in place.

  • Auth, password reset, dashboard and settings
  • Catppuccin and other themes
  • Hot reload and migrations with kumi dev and kumi db migrate
go install github.com/btdstudio/kumi/cmd/kumi@latest
Read the kumi docs on GitHub

hanga

版画

woodblock print

A fast static site generator compatible with Jekyll and Octopress. This site is built with it.

  • Liquid templates and Chroma code highlighting
  • Preview server with rebuild on save
  • Deploys to S3, GitHub Pages or (S)FTP
go install github.com/btdstudio/hanga/cmd/hanga@latest

The method

The folder is the architecture.

daiku implements Interpretable Context Methodology (ICM). Instead of keeping process in a framework, the workspace itself holds it: a room for each kind of work, numbered stages, the persona for each stage, templates and a map at the root.

Your harness reads AGENTS.md and follows the structure. Nothing needs to run after scaffolding, and you can read everything it reads.

ICM is described by Jake Van Clief and David McDermott in "Interpretable Context Methodology: Folder Structure as Agentic Architecture".

# a daiku workspace
├── AGENTS.md
├── STATE.json
├── LOG.md
├── REPOS.json
├── sync.md
├── ideas/
├── references/
├── plan/
│   ├── 00_intake/ … 06_publish/
│   └── specs/
└── build/
    ├── tickets/
    ├── 01_design/ … 04_refactoring/
    └── webapp/changes/

Start with a plan.

go install github.com/btdstudio/daiku/cmd/daiku@latest
daiku init my-workspace
